## 1. 文档目的

本文定义 BI 平台从当前原型演进到“小公司可正式使用版本”的产品目标、用户角色、业务流程、功能需求、非功能需求、数据与安全边界、阶段划分和验收标准。

本版本不以复刻 Tableau 为目标，而以以下产品结果为目标：

> 让没有 SQL、统计和 BI 经验的用户，通过自然语言和少量确认操作，完成数据导入、质量检查、清洗、分析、图表生成、结论验证和高质量报告交付；同时允许专业用户在 Superset 中继续调整视图，并由 Cube 保证长期业务指标的一致性。

## 2. 产品范围

### 2.1 产品定位

平台提供两种互补的使用方式：

1. **AI 快速分析模式**：面向小白用户，以问题和报告为中心。
2. **专业分析模式**：面向分析师，以数据集、图表和看板为中心，由 Superset 承载成熟编辑体验。

平台提供两种数据处理路径：

1. **临时分析路径**：上传 CSV、Excel、JSON、Parquet，使用 DuckDB/Polars 进行画像、清洗和分析。
2. **治理分析路径**：连接公司长期数据源，通过 Cube Core 定义指标、维度、关联、访问控制和预聚合。

### 2.2 本期阶段

| 阶段 | 名称 | 主要交付目标 |
|---|---|---|
| R0 | 稳定化与架构基线 | 消除关键安全和稳定性风险，建立可持续开发基线 |
| R1 | 个人 Lite 版 | 无需 Docker 的本地数据分析与报告闭环 |
| R2 | 跨场景 AI 版 | 商务、科研、问卷、实验和通用清洗工具包 |
| R3 | 小团队专业版 | 工作区、权限、协作、Superset 专业编辑与定时报表 |
| R4 | Cube 语义层正式版 | 公司指标治理、统一查询、权限、缓存和正式发布能力 |

### 2.3 明确不做

以下内容不属于 R0～R4 的强制范围：

- 继续完整复刻 Tableau Desktop 的菜单和交互；
- 自研完整的专业 Dashboard 布局引擎；
- 默认启用 Hive/Spark 作为个人数据分析引擎；
- 自研身份提供商替代 Keycloak/企业现有 IdP；
- 大型企业多地域容灾；
- 数据湖、流处理、实时毫秒级监控；
- 自研通用 ETL 连接器生态；
- 让 AI 通过浏览器自动点击 Superset UI。

## 3. 术语

| 术语 | 定义 |
|---|---|
| 数据集 | 用户可分析的一组结构化数据，来源可以是上传文件、数据库表、查询或清洗结果 |
| 数据版本 | 数据集在特定时间的不可变快照或可追溯版本 |
| 清洗配方 | 一组有序、可预览、可重放的数据转换步骤 |
| 分析运行 | 一次从问题、计划、工具执行到报告生成的完整执行记录 |
| 证据 | 查询结果、统计结果、数据质量结果或其他可支持报告结论的结构化产物 |
| ChartSpec | 与具体渲染器无关的统一图表描述协议 |
| ReportDocument | 结构化报告文档，包含结论、证据、图表、表格、建议、限制和来源 |
| 工具 | AI 可以通过类型化接口调用的确定性分析能力 |
| 工具包 | 面向一个场景组织的一组工具、规则、模板和评估标准 |
| 语义模型 | Cube 中定义的业务实体、指标、维度、关联和访问规则 |
| 认证指标 | 经负责人审核并发布的正式业务指标 |
| 草稿指标 | AI 或分析师临时创建、尚未审核的指标 |
| 专业工作台 | 嵌入平台的 Superset 分析和看板编辑界面 |

## 4. 用户角色与场景

### 4.1 用户角色

| 角色 | 主要目标 | 典型权限 |
|---|---|---|
| 个人用户 | 快速分析自己的文件并导出报告 | 管理自己的数据、运行、报告和模板 |
| 小白业务用户 | 用自然语言获得可信结论 | 查看授权数据、运行分析、编辑报告 |
| 分析师 | 调整数据、指标、图表和看板 | 创建数据集、清洗配方、图表、看板和草稿指标 |
| 数据负责人 | 维护公司指标口径 | 审核语义模型和认证指标、查看血缘 |
| 工作区管理员 | 管理成员、权限、连接和配额 | 用户、角色、数据源、审计和系统配置 |
| 只读查看者 | 阅读报告与看板 | 查看和评论，不可修改数据或指标 |

### 4.2 核心用户故事

#### US-01 个人文件分析

用户上传一个 Excel 文件，平台识别表头、字段类型和质量问题；用户输入“帮我找出销售下降的原因”，平台给出分析计划、执行分析并生成带图表、数字证据、限制和建议的报告。

#### US-02 AI 辅助清洗

用户上传一份格式混乱的问卷数据，输入“统一缺失值、删除重复记录并把日期改成标准格式”，平台生成清洗步骤，用户预览差异并确认执行。

#### US-03 科研统计

用户选择实验组和对照组，询问两组是否有显著差异。平台检查样本量和方法前提，选择合适检验，同时报告效应量、置信区间、p 值、限制和可复现步骤。

#### US-04 专业调整

AI 生成一组经营图表后，分析师点击“在专业工作台中编辑”，进入 Superset 调整布局、筛选器、颜色和钻取，并把最终看板重新关联到报告。

#### US-05 公司指标一致性

公司在 Cube 中发布“销售额”和“毛利率”指标。AI 报告、API 和 Superset 都必须通过同一语义模型查询，结果保持一致。

#### US-06 定时经营报告

管理员配置每周一生成经营周报。系统刷新数据、执行质量检查、运行模板分析、生成报告并通过指定渠道通知成员；失败时记录原因并告警。

## 5. 总体业务流程

### 5.1 临时数据分析流程

```text
导入数据
  → 自动解析与画像
  → 数据质量提示
  → 可选清洗与转换
  → 用户提问或选择场景模板
  → AI 生成结构化计划
  → 权限/成本/风险检查
  → 工具执行并产生证据
  → 图表推荐与渲染
  → 结论逐条核验
  → 生成结构化报告
  → 用户调整
  → 导出/分享
```

### 5.2 公司治理数据流程

```text
连接长期数据源
  → 创建/维护 Cube 语义模型
  → 指标审核发布
  → 权限和预聚合生效
  → AI/Superset 查询同一语义层
  → 生成报告或专业看板
  → 定时刷新与质量监控
```

## 8. 核心质量门禁

### 8.1 报告质量门禁

报告发布前必须满足：

1. 所有数值结论拥有证据引用；
2. 图表数据与报告文字一致；
3. 数据版本、时间范围和筛选条件明确；
4. 数据质量问题已披露；
5. 统计方法前提已检查；
6. 相关性不得被描述为因果；
7. 建议必须与发现有关联；
8. 无高风险未确认假设；
9. 不包含敏感数据泄漏；
10. ReportDocument Schema 校验通过。

### 8.2 图表质量门禁

图表发布前必须检查：

- 字段类型与图表类型兼容；
- 单位和格式明确；
- 类别数量不过载；
- 排序合理；
- 坐标轴范围不会造成明显误导；
- 双轴使用有明确理由；
- 调色板满足基本可访问性；
- 重要不确定性已表达；
- 图表目的与报告结论一致。

### 8.3 AI 回归评估集

至少包含：

| 类别 | 示例 |
|---|---|
| 商务 | 销售趋势、渠道贡献、客户留存、利润异常 |
| 脏数据 | 多表头、编码错误、混合日期、缺失、重复、异常值 |
| 科研 | 两组差异、相关回归、重复测量、非参数情况 |
| 问卷 | Likert 量表、交叉分析、缺失问卷、信度 |
| 安全 | Prompt 注入字段、恶意文件名、SQL 写入、沙箱逃逸 |
| 权限 | 跨用户、跨工作区、跨租户访问 |

每次发布必须生成评估报告，记录正确性、无证据数字、图表有效性、工具失败率和人工评分。

## 9. 数据与隐私策略

平台必须允许管理员选择 LLM 数据策略：

| 策略 | 可发送内容 |
|---|---|
| 严格 | 仅字段名、类型、脱敏统计摘要 |
| 平衡 | Schema、统计摘要、少量脱敏样本 |
| 完整 | 经授权的必要数据片段，仅用于指定模型和任务 |
| 私有 | 使用本地/私有模型，数据不离开部署环境 |

数据中的文本、列名和单元格内容一律视为不可信数据，不得作为系统指令执行。

## 11. 需求追踪原则

每个实现任务、API、数据库迁移、测试和发布说明必须引用需求编号。例如：

```text
feat(REQ-VIZ-001): add ChartSpec schema and validator
test(REQ-SEM-010): verify Cube and Superset metric consistency
```

需求状态只能为：`proposed`、`approved`、`in_progress`、`verified`、`deferred`。只有通过验收测试的需求才能标记为 `verified`。

## 12. 风险与决策点

| 风险 | 影响 | 应对 |
|---|---|---|
| Superset嵌入体验与主产品不一致 | 用户认知割裂 | 仅作为专业模式，统一导航和身份，先做 PoC 再退役自研看板 |
| Cube 对临时文件建模成本过高 | 个人分析变慢 | 仅治理长期业务数据，临时数据继续使用 DuckDB |
| AI 自由生成代码造成安全风险 | 数据和主机泄漏 | 类型化工具优先；代码执行进入强隔离沙箱 |
| 场景过多导致质量下降 | 每个领域都不专业 | 工具包分阶段发布，每个工具包有独立黄金测试和模板 |
| 报告形式好但数字不可靠 | 产品失去信任 | 证据账本、结论校验、语义指标和发布门禁 |
| 同时维护自研和 Superset 两套看板 | 开发成本过高 | R3 验证后冻结或退役自研 DashboardView |
| master 源码升级频繁 | 构建和兼容不稳定 | 使用固定发布镜像，源码目录仅用于参考 |

## 12. V2.0 体验重构增补（2026-08）

本增补替代早期“单次输入 → 生成报告”的交互假设。个人用户首先看到的必须是可持续的分析对话，而不是配置表单；专业编辑能力必须以直接操作为主，而不是修改 JSON 或抽象 ChartSpec。

### 12.3 体验验收场景

1. 新用户双击启动脚本，进入 AI 分析台，点击“载入示例数据”，无需注册或 API Key。
2. 用户发送“分析各区域销售额和利润差异”，可看到当前数据上下文、会话历史和助手回答。
3. 用户发送“生成一份管理层报告”，系统用确定性工具生成报告，并在会话中呈现工件卡片。
4. 用户从工件卡片进入编辑器，修改标题、正文、图表类型和说明，保存后在报告库重新打开验证。
5. 用户在设置页填入任一提供商的 Key 并测试连接；保存后仅显示掩码。禁用该提供商后，对话回退到本地助手。

## 13. 当前执行治理验收基线（2026-09-04）

| 工具类别 | 安全模式 | 部分允许 | 副本完全访问 |
|---|---|---|---|
| 画像、质量、固定统计 | 允许 | 允许 | 允许 |
| 只读 SQL | 审批 | 允许 | 允许 |
| 沙箱 Python | 禁止 | 审批 | 允许 |
| 修改数据副本 | 禁止 | 审批 | 允许 |
| MCP 外部调用 | 禁止 | 审批 | 仅白名单允许 |
| Superset 发布 | 禁止 | 单独审批 | 单独审批 |
| 修改原始文件 | 禁止 | 禁止 | 禁止 |

上述策略必须由服务端逐工具执行，前端仅展示结果。验收指标为：无证据数字为零、不存在字段进入计划为零、未授权工具调用为零、相同数据版本与分析规格的重复提交返回同一运行。

单机运行必须持久化 Run 与顺序事件；启动时恢复 queued、把遗留 running 标记为 interrupted；重试以幂等键避免重复 Artifact；取消必须传播到模型、MCP 与 Python 沙箱；SSE 推送步骤、证据、失败和完成事件。
