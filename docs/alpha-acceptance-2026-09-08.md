# Alpha 真实对照与故障验收 · 2026-09-08

结论：数值基线可靠，需求能够改变计划与篇幅，但专题聚焦、补算语义、总结忠实度仍不足。本轮不能宣布五组业务验收全部通过，也不能宣布已经达到稳定开源发行版。

## 测试方法与证据

真实模型为本机已配置的 `deepseek-v4-flash`，五组均只执行第一次请求，没有失败后反复重试到绿。使用异步规划和异步执行 API，权限为部分允许，补充分析上限三轮，开启内容审阅与布局，关闭多方案，不做外部发布。

使用 SQLite 只读备份到独立目录，复制已选 CSV 和加密设置所需密钥；原始数据库不修改，用户服务不重启。注意备份是整库快照，不是只导出模型设置，含其他历史记录；该目录不应公开或打包发布。复制的历史排队/运行任务先停用，避免验收实例恢复用户历史任务。

本地证据：`data/acceptance/20260908-170930-alpha/`。

- `suite.json`、每组 `acceptance.json`：保留原始自动判定。
- 每组 `plan.json`、`planning-run.json`、`execution-run.json`、`answer.json`、`report.json`：真实过程与输出。
- `source-snapshots.json`：源文件 SHA256、版本和路径。
- `adjudication.json`：独立复算及修正后的技术判定，不覆盖原始失败记录。

初始验收脚本误把保留五位小数的利润与两位小数基准作严格比较，导致三个 Superstore 用例先记 failed。修复脚本的比较精度后，另以 Python 标准库 CSV + Decimal 从源数据复算，不再付费重跑。

独立结果：51,290 行，销售额 12,642,905，利润 1,467,457.29128，负利润记录 12,544 条，亏损绝对额 920,646.15572。负利润按 Region 汇总最高是 Central，202,196.36690，而不是对全部记录净利润排名。

Bike 关联副本 17,379 行，累计需求 3,292,679，包含 731 个日期；按日期核对小时累计与唯一日级值，非零差额日期为 0、最大绝对差额为 0，无重复日期+小时。此检查仅证明关联副本内一致性，不证明原始两表的未匹配记录覆盖。

## 人工内容检查

### 经营简报：不通过

确实压缩到八块，但保留的图表只有销售额、利润和数量 KPI，结构对比不足。模型生成了不存在的 `Customer_ID`（实际为 `Customer ID`），一条 SQL 失败；总结引用了不存在或冲突的 fact_id，明确降级到本地结论。计划还把报告、排版、审阅排在后续 SQL 之前，报告无法吸收这些后续查询结果。总额正确不能掩盖这些问题。

### 亏损专题：部分满足，不算完整通过

计划 SQL 确实筛选 `Profit < 0`，区域汇总与产品明细均执行成功。报告有亏损绝对额、负利润记录数，与普通经营报告不同。

但补算工具只接收 dimension/measure，没有保持负利润筛选，三轮实际返回的是全部记录的净利润最高项。报告最终用 Category 亏损分布替代了用户要求的 Region 集中项，已成功执行的区域 SQL 未进入专题正文。总结还把“折扣与利润负相关”改成“亏损额/亏损与折扣负相关”，指标语义发生变化。

### 详细报告：部分满足，不算完整通过

包含区域贡献、折扣档位与亏损 SQL，扩充到 33 块、9 个图表对象，路径与简报不同。但补算把 Discount 比例直接求和并按贡献排序，不适合作为折扣强度。正文的 SQL 补充仍主要是“返回几行，见证据”，未充分解释结果；“利润率偏低”没有行业或目标基准。需防止篇幅增加但信息价值未增加。

### 小时需求：部分满足

48 行小时×工作日查询成功，观测小时数、均量、缺失小时不补零的口径正确。补算明确选择 hr、workingday、weekday，比商务报告更贴题。

最终仅一张工作日均量图，没有核心的小时×工作日需求曲线。总结把各自的边际结果组合成“工作日傍晚峰值”，所引用事实没有绑定同一个交叉分组结果；泛化的季节解释仍较多。这是证据存在但不足以支撑该具体措辞的例子。

### 多表核对：不通过，原自动判定是假阳性

计划识别了逐日汇总、关联与差额覆盖统计，比小时需求计划不同。但两条 CTE SQL 被 N:1 非可加字段保护拦截；仅剩的日期汇总预览截断为 300 行。补算误将按月份需求分解当作核对，并在停止理由中声称证据充分。

总结仍声称“覆盖完整、无重复累计风险”；当前正式证据只支持总量相等和粒度说明，不能推出所有日期均匹配。报告又塞入趋势、季节和天气等七个图表对象，专题不聚焦。后续应提供独立原表粒度的核对工具，而非关闭 N:1 保护。

### 共性结论

不是“所有提示词输出完全相同”，而是**规划已有差异，执行器与报告组装仍会丢失这些差异**。当前 `synthesis_validation=verified` 仅表示结构/引用协议通过，不能称为语义正确；摘要没有逐项证据绑定，定性文字仍会偷换指标、扩大范围。审阅模型也会出错，例如要求互相重叠的不同维度占比加起来等于百分之百，不应机械应用审阅建议。

## 本轮实现与故障结果

- 修复规划重试幂等：同一前序 Run 使用稳定键，唯一约束及 savepoint 防止重复占位消息。重复点击回归通过。
- 规划/执行取消：注入阻塞协程，确认 cancelled、无结果报告、无完成事件，对话记录保留。
- 断网：在模型调用边界注入 ConnectError，不断开用户网络；验证 fallback/degraded。新增报告降级门槛，不把失败链路的局部产物标为完整交付。
- 真正进程退出：强制终止测试专属 uvicorn 子进程，再以相同独立数据目录启动；running → interrupted，queued → completed，消息 ID 保留，没有伪报告。
- 新增 `execution_outcome`，分离“生命周期结束”与“部分工具失败/总结降级”；保存到回复、报告和 Run progress，显示警告。兼容旧 completed 状态，不改历史数据。语义错误尚不能全部自动识别。
- `report.layout` 经统一内置扩展注册接口执行，保留版本、能力开关和原有权限/持久化边界。
- 新增执行重试的产物断言：同一前序任务连续重试、完成后再次点击旧重试，均返回相同新 Run；只生成一个报告 Artifact、一个版本。扩展执行失败不污染输入草稿也有回归覆盖。
- 浏览器测试捕捉到报告搜索的延迟窗口中“全选”可能选中空列表；加载标记提前至搜索变更时，加载期间禁用选择/批量操作，回归等待实际查询响应后验证两项均被勾选。

限制：取消测试覆盖规划/执行协程边界，不代表已实测远端模型停止计费、所有 Python 子进程和 MCP 服务的取消；本轮进程退出发生在规划阶段，尚未覆盖报告文件写入与 DB 提交之间的所有断电窗口；重复重试验收覆盖连续点击，尚需高并发重试压力测试。不可据此承诺所有故障下零重复产物。

## 下一轮应收敛的三个目标

1. **保留需求语义到最后一步**：任务目标拆为可验收 obligations；规划依赖排序；分析工具接收已验证筛选器与聚合语义；比例拒绝默认 SUM；专题正文优先纳入已成功的相关查询。
2. **核对专用能力与总结门槛**：原表逐日汇总、覆盖、差额、重复键 → 有边界的结构化证据；摘要和解释绑定指标/范围/分组，失败步骤与预览截断必须进入总结 Context Packet；总量相等不能推出逐项相等。
3. **复测而不是扩图**：先将本轮失败样本变为离线回归，再以同五个请求做下一次真实对照，单独记录新尝试与 Token；补执行写入窗口故障和干净 Windows/真人首用验收。

不建议此时扩插件市场、引入更多 Agent 或增加一层自动重试。最小扩展说明见 [minimal-extensions.md](minimal-extensions.md)。
